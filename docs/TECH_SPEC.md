# BeautyTalk 기술 명세서

무엇을 썼고, **그걸로 어떻게 만들었는지**를 적는다.
버전은 `pubspec.lock` 과 `server/requirements.txt` 가 기준이다 — 여기 적어 두면 금방 낡는다.
화면 동작과 개편 규칙은 [README.md](../README.md), [REDESIGN_CONTRACT.md](REDESIGN_CONTRACT.md).

**BeautyTalk** — 시각장애인·저시력 사용자용 메이크업 도우미.
화장품 인식은 기기 안에서, 메이크업 분석은 팀 노트북 GPU 서버에서 처리한다.

---

## 2. 화장품 인식 — 어떻게 만들고 어떻게 돌리나

### 2.1 모델을 어떻게 만들었나

MobileNetV3-Small 백본 하나에 **헤드를 둘** 붙였다.

- `det_head` — CenterNet-lite, stride 8, 19클래스. 출력은 히트맵 `hm[1,48,48,19]` 과
  크기 `wh`, 중심 오프셋 `off`. sigmoid 는 내보내기 그래프 안에 넣었다.
- `cls_head` — 렌즈 clean/dirty 2클래스. raw logits 로 내보내고 softmax 는 앱에서 한다.

처음에는 검출 모델과 렌즈 모델을 따로 뒀다가, **단일 그래프로 합쳤다.** 그래야 사진 한 장에
추론 한 번으로 둘 다 나온다.

변환은 3단계다.

```
runs/mt11/best.pt
  └─ src.export  --size 384        → mtnet_both.onnx      (NCHW 1×3×384×384)
       └─ onnx2tf -nuo             → mtnet_both.tflite    (NHWC 1×384×384×3)
            └─ assets/models/cosmetic_both.tflite  (4.77MB)
```

변환할 때마다 ONNX 출력과 TFLite 출력을 같은 입력으로 비교해 **비트 동등(오차 `1e-7`)** 을
확인했다. 레이아웃이 NCHW → NHWC 로 바뀌는 구간이라, 여기서 확인하지 않으면 앱에서 조용히
엉뚱한 답이 나온다.

> 변환 환경은 `numpy` / `protobuf` 핀이 예민하다. 같은 venv 에 MediaPipe 를 설치하면
> 두 패키지가 조용히 내려가서 TensorFlow 가 import 조차 되지 않는다. MediaPipe 는 별도 venv 에 둔다.

### 2.2 앱에서 어떻게 돌리나

1. **로드** — `.tflite` 를 에셋에서 인터프리터로 올리고, `labels.txt` 를 읽는다.
   출력 텐서는 인덱스를 하드코딩하지 않고 **shape 와 이름으로 식별**한다 — 클래스 수만큼
   채널이 있으면 히트맵, `[1,2]` 면 렌즈 logits, 이름에 `off`/`wh` 가 있으면 그쪽.
   변환 도구가 출력 순서를 바꿔도 앱이 안 깨진다.
2. **전처리** — 아이솔레이트(`compute`)에서 돈다. EXIF 회전을 굽고, 384×384 로 리사이즈한 뒤
   RGB `0..1` NHWC **평탄 `Float32List`** 로 만든다. 검출 모델이라 **크롭하지 않는다** —
   물체가 잘리면 안 된다. mean/std 정규화는 그래프 안에 있으므로 앱에서 하지 않는다.
3. **추론** — 입력·출력 모두 **바이트 버퍼**로 주고받는다. 중첩 List 를 넘기면 스칼라마다
   4바이트 버퍼를 만들어 이어붙이는데(44만 번), `Uint8List` 는 그대로 memcpy 하는 빠른
   경로를 탄다. 출력도 네이티브 버퍼를 `Float32List` 뷰로 직접 읽어 복사를 없앴다.
4. **디코드** — 히트맵 전체에서 전역 최고점 하나만 찾아 (클래스, 신뢰도)로 쓴다.
   NMS 없이 top-1 만 — 사용자가 물건 하나를 들고 찍는 상황이다.
   `0.30` 미만이면 `unknown` 으로 두고 억지로 답하지 않는다.
5. **근거 박스** — 결과 화면에 "어디를 보고 판단했는지" 그리려고 CenterNet 디코드를 한다.
   최고점 셀의 `off` 로 중심을, `wh × stride` 로 크기를 복원한 뒤 `0..1` 로 정규화한다.
   입력이 원본을 통째로 384 로 리사이즈한 것이라, 그 좌표를 원본 사진에 그대로 얹을 수 있다.
6. **폴백** — 모델 파일이 없거나 로드에 실패하면 Mock 분류기로 자동 전환한다. 모델 없이도 앱은 뜬다.

픽셀 순서가 틀리면 모델은 예외를 내지 않고 **조용히 틀린 답**을 낸다. 그래서 `(y,x,c)` 배치를
`test/preprocess_test.dart` 가 따로 검증한다.

### 2.3 렌즈는 어떻게 판정하나

`cls_head` 만으로는 못 잡았다. 실제 젖은 렌즈 3장 중 1장만 잡았고(0.97 / 0.03 / 0.03),
반대로 깨끗한 렌즈로 찍은 점박이 천장 타일을 0.78~0.92 로 "더럽다"고 했다 — 점을 얼룩으로 읽는다.

그래서 **고전 신호를 함께 쓴다.** 전처리가 만든 배열을 회색조로 바꿔(PIL 과 같은 luma 계수)
라플라시안의 분산, 즉 선명도를 잰다. 판정은 이렇게 합친다.

| 선명도 | 판정 |
| --- | --- |
| 낮다 | 더럽다 — 물 번짐·뿌연 막. **모델이 뭐라 하든** |
| 아주 높다 | 깨끗하다 — 젖은 렌즈는 이렇게 선명할 수 없다. **모델이 뭐라 하든** |
| 그 사이 | `softmax(cls_logits)` 의 dirty 확률로 결정 |

실측이 갈라 준다 — 젖은 렌즈는 전부 30 아래, 깨끗한 렌즈는 121 이상이었다.

렌즈 검사만 **가운데 크롭**을 쓴다. 세로 프레임을 정사각으로 찌그러뜨리면 물 자국 결이
뭉개져서 같은 프레임이 0.52(문턱 아래)로 떨어지는데, 크롭하면 0.97 로 잡힌다.

검사 시점은 탭에 들어올 때 1회 + **셔터를 누를 때마다**다. 더러우면 촬영을 접고 닦으라고 말한다.

## 3. 메이크업 분석 — 어떻게 갈라 태우나

### 3.1 GPU 한 장에 경로 둘을 어떻게 올렸나

립 경로와 메이크업 경로가 **같은 베이스 체크포인트**를 쓴다는 점을 이용했다.
모델은 한 벌만(약 7.7GB) 올리고 어댑터만 갈아 끼운다.

| 경로 | 전처리 | 어댑터 | 프롬프트 | few-shot |
| --- | --- | --- | --- | --- |
| `lip` | 입술 크롭 | 없음 — 어댑터를 **끈다** | 립 프롬프트 | 3장 |
| `makeup` | 얼굴 크롭 | 메이크업 LoRA | 메이크업 프롬프트 | 0장 |

전환은 `set_adapter()` 로 어느 어댑터를 쓸지 고르고, 립 경로에서는 `disable_adapters()` 로
통째로 꺼서 순수 베이스로 돌린다 — `set_adapter()` 만으로는 꺼지지 않는다.
포인터 교체 수준이라 사실상 공짜다. 두 벌 올렸다면 VRAM 이 두 배 든다.

립 경로에 어댑터가 없는 것은 의도다 — 인계 문서가 "파인튜닝 없음, 시스템 프롬프트 +
few-shot 3장으로만 동작"이라고 명시한다.

> 8B 를 4B 로 내리지 말 것. 립 프롬프트와 few-shot 3장이 8B 기준으로 검증된 세트이고,
> 메이크업 LoRA 는 8B 위에서 학습돼 교체가 불가능하다. few-shot 3장도 세트다 —
> 1장 교체로 정상 판별이 10/14 → 7/14 로 무너진 사례가 있다.

### 3.2 요청을 어떻게 흘리나

스레드풀을 **둘로 나눴다.** 전처리용 풀(워커 여럿)과 GPU 풀(워커 1개)이다.
GPU 쪽은 풀 자체가 1개 워커이고, 엔진 안에서도 락으로 생성을 직렬화한다.

```
업로드 → MediaPipe 크롭 [전처리 풀, 중앙값 13ms]
           ├ 못 쓸 사진 → 재촬영 안내를 그대로 돌려준다. GPU 안 씀
           └ 쓸 만함  → GPU 풀 [1장, 직렬] → 생성 → 새니타이즈
```

전처리를 GPU 워커 안에 넣지 않은 이유가 핵심이다. 앞이 보이지 않는 사용자에게 프레이밍
실패 반복은 **정상 사용 패턴**이라, 안에 넣으면 어차피 실패할 요청이 GPU 슬롯을 잡아먹는다.
지금 구조에서는 재촬영 안내가 GPU 를 기다리지 않고 수십 ms 만에 나간다.

MediaPipe 검출기는 스레드로컬로 만든다 — 워커마다 하나씩 들고 있어야 안전하다.

재촬영 판정은 밝기·얼굴 유무·입술 폭·얼굴 폭 네 가지이고, 안내 문구는 가공 없이 그대로
TTS 로 나간다.

### 3.3 경로를 어떻게 고르나

모델이 아니라 규칙이다. 질문을 정규화(NFC, 공백·기호 제거)한 뒤 순서대로 본다.

1. 배제 표현("립 말고", "입술 빼고") → 메이크업
2. 립 단서(립·입술·틴트·입꼬리…) → 립
3. 메이크업 단서(눈썹·피부·볼·전체…) → 메이크업
4. 단서 없음 → 메이크업(기본값)

키워드에 오타 변형(입슬·입쑬·맆)을 직접 넣어 뒀다 — **STT 오인식 대응**이다.
여기서 잘못 고르면 크롭도 프롬프트도 어댑터도 전부 어긋나는데 사용자는 화면을 못 보므로
조용히 틀린다. 그래서 라우팅만 따로 테스트한다.

### 3.4 답을 어떻게 다듬나

생성문을 그대로 읽히지 않는다. TTS 안전 필터를 한 번 통과시켜 읽을 수 없는 형식을 걷어내고,
실패하면 폴백 문장으로 바꾼다. 앱은 최종 문장만 받는다.

## 4. 앱과 서버를 어떻게 연결했나

1. **서버 찾기** — `/health` 를 8100 → 8000 순으로 두드려 `healthy` 를 주는 쪽을 고른다.
   응답의 `analyzer` 값도 같이 읽어서, mock 서버에 붙어 있다가 실모델이 뜨면 **다시 탐색해
   갈아탄다.**
2. **붙기** — 고른 주소로 `ws://…/ws/{session_id}` 연결. 세션 ID 는 앱 실행마다 새로 만든다.
3. **사진 싣기** — 아이솔레이트에서 EXIF 회전을 굽고, 긴 변이 1280px 을 넘으면 줄인 뒤
   JPEG 로 인코딩해 base64 로 만든다. WebRTC 대신 **스냅샷** 방식이다.
4. **보내기** — `request_id` 를 붙여 보내고, 그 ID 로 `Completer` 를 걸어 둔다. 응답이 오면
   ID 로 짝을 찾아 깨운다. 요청이 겹쳐도 섞이지 않는다.
5. **기다리기** — 앱은 70초, 서버는 60초. **앱이 더 길어야** 다 만든 답을 버리지 않는다.
   타임아웃이 나면 소켓을 끊어 버린다 — 흔한 원인이 Tailscale 순단으로 생긴 유령 연결이라,
   끊어야 다음 시도가 새로 접속한다.
6. **읽기** — 앱은 `message` 만 TTS 로 내보낸다. `status` 가 `retake` 여도 그대로 읽으면 된다 —
   재촬영 안내 문장이다. 화면 카드용 항목은 따로 오지만, **음성은 항목을 이어 붙이지 않는다.**
   다시 문장을 만들면 낭독과 화면이 어긋난다.

```jsonc
// 앱 → 서버
{ "type": "analyze", "request_id": "...", "question": "립 어때?",
  "image_b64": "...", "mirrored": false }

// 서버 → 앱
{ "type": "analysis_result", "request_id": "...",
  "status": "ok",            // ok | retake | error
  "message": "읽어줄 문장",   // 앱은 이것만 읽는다
  "route": "lip", "prep_ms": 14, "infer_ms": 3120 }
```

**이 스키마는 변경 금지 구간이다.** UI 를 개편해도 한 글자도 바뀌지 않는다.

**촬영 전 확인** — 셔터를 누르면 같은 인코딩으로 `/framing` 에 먼저 물어본다.
분석과 **같은 크기로** 보내야 한다 — 서버가 픽셀 단위로 판정하므로 여기서 작게 보내면
통과해 놓고 본 촬영에서 재촬영이 뜬다. 서버가 없거나 실패하면 그냥 촬영을 진행한다.

**GPU 깨워 두기** — 절전으로 내려간 GPU 는 첫 추론이 30~60초 걸린다. 앱 기동 때 한 번,
메이크업 탭에 들어올 때 한 번, 탭에 머무는 동안 주기적으로 `/warmup` 을 부른다.
분석 요청 자체도 GPU 를 최대로 돌리므로 warm 으로 쳐서 불필요한 호출을 막는다.

**서버가 없으면** 실패를 말하고 촬영으로 돌아간다. 대체 답변을 지어내 읽지 않는다 —
매번 같은 문장이 나와 "캐시된 답"처럼 들리고, 앞이 보이지 않는 사용자에게 가짜 분석은
오답보다 나쁘다.

## 5. 음성을 어떻게 듣고 어떻게 말하나

**듣기** — 마이크는 평소 꺼 둔다. 화면을 두드린 순간부터 **한 문장만** 듣고 스스로 멈춘다.
주변 대화가 계속 들어오지 않고 배터리·프라이버시에도 유리하다.

인식 정확도는 세 가지로 메운다.

1. STT 가 주는 **2·3순위 후보까지 전부** 명령과 대조한다.
2. 한글을 **자모로 분해해 편집거리**로 비교한다 — 조금 틀리게 들려도 동작한다.
3. 최종 결과를 기다리지 않고 **부분 인식 단계에서 즉시** 반응한다. 체감이 빠르다.

무음으로 꺼질 때는 "못 들었어요" 라고 말한다. 조용히 꺼지면 사용자는 죽은 마이크에 대고
계속 말한다. 한국어 온디바이스 언어팩이 없으면 앱 시작 때 다운로드를 요청한다(Kotlin 채널).

메이크업 탭에서는 주변 대화가 그대로 서버로 가지 않도록, **질문형 어미나 트리거 단어가
있을 때만** 전송한다.

**말하기** — 기기의 한국어 **오프라인** 음성만 쓴다. `-network` 판은 인터넷이 끊기면 침묵하고,
`kok-*` 는 한국어가 아니라 콘칸어라서 후보에서 뺐다. 설정 탭에서 음성·속도·음높이를 고르면
파일에 저장돼 다음 실행에도 유지된다. 기기에 그 음성이 없으면 다음 후보로, 다 없으면 기기
기본 음성으로 넘어간다.

## 6. 앱을 어떻게 짰나

| 항목 | 방식 |
| --- | --- |
| 상태 | `AppState`(ChangeNotifier) **하나로 모았다**. 외부 상태관리 패키지 없음 |
| 서비스 | 전부 싱글턴 — 어디서든 `VoiceService.instance` 로 접근 |
| 입력 | 화면 **전체**에 제스처를 건다 — 탭(음성) / 더블탭(촬영) / 롱프레스(종료) |
| 무거운 연산 | 이미지 전처리·스냅샷 인코딩은 아이솔레이트로 뺀다 |
| 색·글꼴 | 토큰 파일 한 곳에만 둔다. 화면 코드에 hex 를 쓰지 않는다 |
| 로그 | `debugPrint` 를 후킹해 파일로 남긴다 |

버튼을 찾을 필요가 없게 만든 것이 입력 설계의 핵심이다. 어디를 두드려도 되므로
"어느 쪽을 눌렀는지 모르는" 상황이 생기지 않는다.

**로그를 둘로 나눈 이유** — 인식된 문장은 `app.log` 에 넣지 않고 `speech.log` 에 최근 몇 건만
남긴다. 시연장에서 오간 주변 대화가 파일에 통째로 쌓이지 않게 하면서, 방금 뭘 잘못
알아들었는지는 볼 수 있게 했다. 촬영 사진도 캐시에 최근 몇 장만 남기고 지운다 —
탭 진입마다 렌즈 검사로 1장, 촬영마다 1장이 생겨서 안 지우면 시연 한 번에 수백 장이 쌓인다.

**패키지** — `tflite_flutter`(추론), `camera`, `speech_to_text`, `flutter_tts`,
`image`(전처리·인코딩), `web_socket_channel`, `http`, `permission_handler`, `path_provider`,
`audioplayers`(연출 효과음). 한글 글꼴은 번들하지 않고 기기 기본을 쓴다 —
Noto Sans KR 을 넣으면 굵기당 5MB 씩 늘어나는데 모양은 같다.

## 7. 분석 연출을 어떻게 만들었나

서버 응답을 기다리는 수십 초를 채우는 연출이다. 사진이 격자가 되고, 격자가 3D 아바타로
떠올라 부위별로 짚인다.

**굽는 순서**

1. MediaPipe FaceLandmarker 로 얼굴 격자(478점)를 뽑아 사진 안 `0~1` 좌표 JSON 으로 저장한다.
2. Blender(`bpy`)에서 메시를 만든다. 격자는 얼굴 앞면만 있는 껍데기라 그대로 돌리면 가면이
   누워 있는 것으로 보인다 — 테두리를 뒤로 밀어 **뒤통수를 닫고**, 관자놀이 뒤가 얼굴보다
   넓어지게 부풀린다. 그러지 않으면 아무리 돌려도 머리가 얼굴 윤곽 뒤에 가려진다.
3. 이목구비 윤곽선은 격자와 같은 굵기로 그리면 묻히므로 **별도 객체로 빼서 굵게** 뽑는다.
4. 렌더한 프레임에 Pillow 로 빛 번짐과 알파를 입힌다.
5. **알파 있는 애니메이션 WebP** 한 장으로 굽는다 — `Image.asset` 만으로 재생되므로 영상
   플러그인이 필요 없다.

**앱에서의 재생** — 한 컨트롤러의 진행률로 빔 → 격자 → 특징점 고정 → 유지 → 사진 소멸 →
3D 변형 → 부위 지시 구간을 나눠 그린다. 격자가 사진에서 차지하던 사각형에 아바타를 맞춰야
"그대로 떠오른" 것으로 보인다. 어긋나면 "바뀌었다"가 아니라 "잘렸다"로 보인다.

**소리** — 음원은 받아온 게 아니라 Python 표준 `wave` 로 합성했다. 원샷 플레이어는 4개를
풀로 돌려 쓴다(매번 새로 만들면 특징점이 촘촘할 때 수십 개가 쌓인다).
**소리는 항상 TTS 아래로 깐다** — 지속음인 hum 은 원래 작고, TTS 가 말을 시작하면 한 번 더
낮춘다. 안내를 덮는 순간 이 연출은 앱을 망가뜨린다.

**사진측량은 실패했다.** COLMAP 으로 눈높이 한 바퀴 영상을 돌렸더니 카메라 복원 자체는
좋았는데(재투영 오차 0.93px) **복원된 것은 사람이 아니라 사무실**이었다. 머리가 있어야 할
자리만 구멍이었다 — 매끈한 피부에는 추적할 질감이 없고 검은 머리는 빛을 먹는 반면
책상·창틀·바닥 타일은 특징이 넘친다. 그래서 지금은 사진을 지우지 않고 **실제 얼굴 위에
격자를 얹는다.** 사진이 그대로 보이니 사진측량 없이도 "그 사람"으로 읽힌다.
파이프라인은 남아 있어 촬영본이 개선되면 그대로 쓸 수 있다.

## 8. 주요 수치

| 항목 | 값 |
| --- | --- |
| 화장품 인식 정답률 | **71.8%** (161장, 임계값 0.30) |
| 임계값 0.40 으로 올리면 | 오답 33건 → 19건, 대신 "못 찾음" 증가 |
| ONNX ↔ TFLite 변환 오차 | `1e-7` (비트 동등) |
| 서버 전처리 | 중앙값 13ms |
| 서버 추론 | 정상 20~35초 (타임아웃 60초, 앱은 70초) |
| 첫 추론(GPU 절전 시) | 30~60초 — warm-up 으로 회피 |
| 렌즈 선명도 실측 | 젖음 16·25·29 / 깨끗 121 이상 |
| 립 경로 "덜 펴발림" 판정 | 4/11 |

선명도 수치는 **이 앱의 전처리 기준**이다. 파이썬 PIL 로 재면 안티앨리어싱 때문에 절반쯤
나오므로 섞어 쓰면 안 된다. 임계값·타이밍 상수는 코드가 기준이다 —
`lib/ml/model_config.dart`(모델), `lib/services/backend_service.dart`(통신),
`server/beautytalk/config.py`(서버).

## 9. 알려진 한계

| 구분 | 내용 |
| --- | --- |
| 플랫폼 | Android 전용. iOS 설정 없음 |
| NPU | QNN/NNAPI delegate 미적용 — 현재 CPU 4스레드. 붙일 훅만 있다 |
| 네트워크 | 메이크업 분석은 서버 필수. 화장품 탭은 온디바이스라 영향 없음 |
| 렌즈 판정 | 무늬 없는 벽이나 어두운 방을 비추면 깨끗해도 걸릴 수 있다 |
| 립 경로 | "덜 펴발림" 판정은 프롬프트로는 상한. 개선은 파인튜닝 영역 |
| 메이크업 프롬프트 | 임시본. 어댑터 저장소에 학습 원문이 없어 립 프롬프트 원칙을 얼굴 전체로 넓혀 새로 썼다 |
| 메이크업 크롭 | 얼굴 크롭 패딩은 검증된 값이 아니다 (립 크롭과 달리 기준 데이터가 없다) |
| 미러링 | 전면 카메라 좌우 반전은 픽셀에 구워져 EXIF 에 남지 않아 코드로 판별할 수 없다. 틀리면 좌우 안내가 통째로 뒤집히는데 사용자가 스스로 확인할 수 없다 — 배포 전 실측 필요 |
| 데이터 정책 | 얼굴 사진 보존 정책이 없다. 현재 서버는 아무것도 저장하지 않는다 |

### 문서 간 불일치 (이 명세서 기준으로 정정)
